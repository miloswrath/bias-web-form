# Form Constitution

## Core Principles

### I. Tech Stack Adherence (NON-NEGOTIABLE)

The project MUST use only the approved tech stack. No new frameworks, libraries, or runtimes
MAY be introduced without an explicit constitution amendment.

**Approved stack:**
- **Runtime**: Node.js (via Nix flake)
- **Framework**: Next.js 16
- **UI**: React 19 + TypeScript 5
- **Styling**: Tailwind CSS v4
- **Database client**: @supabase/supabase-js v2
- **Linting**: ESLint (eslint-config-next)

**Rationale**: Scope creep through dependency sprawl is a primary source of complexity and
maintenance burden in student projects. A locked stack keeps the codebase comprehensible
and reviewable within a single semester.

### II. Unit Tests Only (NON-NEGOTIABLE)

All automated tests MUST be unit tests. Integration test suites, end-to-end tests, and
contract tests MUST NOT be written or required.

**Rules:**
- Tests MUST be isolated — no real network calls, no real database connections.
- Tasks generated by /speckit.tasks MUST NOT include integration or contract test tasks.
- Test tasks are OPTIONAL and only included when explicitly requested in the feature spec.

**Rationale**: A full test suite is disproportionate overhead for a semester-scoped project.
Unit tests provide fast feedback with minimal infrastructure requirements.

### III. Database Safety (NON-NEGOTIABLE)

The production Supabase database MUST NEVER be written to during development or testing.

**Rules:**
- All migration testing MUST target a local Supabase development server (assumed always running).
- Environment variables MUST distinguish local vs. production credentials; only local credentials
  MAY be used in dev/test contexts.
- Destructive schema changes MUST be tested locally before any production migration is considered.

**Rationale**: The production database may contain real or graded data. An accidental write or
dropped table cannot be undone and could affect course deliverables.

## Quickstart Requirements

Every feature MUST include a `quickstart.md` (or equivalent section in `plan.md`) with concrete,
copy-pasteable instructions for verifying the feature works end-to-end against the local
Supabase instance.

**Requirements:**
- Instructions MUST assume the local Supabase dev server is already running.
- Each step MUST be a specific command or browser action — no vague "run the app and check" steps.
- The quickstart MUST cover at minimum: running migrations locally, starting the Next.js dev
  server, and the exact user action that exercises the new functionality.

**Rationale**: Without concrete validation steps, reviewers and future contributors cannot
verify that a feature actually works as described.

## Development Workflow

- All feature work MUST be done on a branch; direct commits to `main` are prohibited.
- Each feature branch MUST have a corresponding spec in `specs/`.
- The local Supabase dev server MUST be used for all database operations during development.
- `npm run lint` MUST pass before any code is considered complete.

## Governance

This constitution supersedes all other practices, conventions, or verbal agreements. Any
deviation from a NON-NEGOTIABLE principle requires a formal constitution amendment (version
bump + documented rationale).

**Amendment procedure:**
1. Edit this file with the proposed change.
2. Increment `CONSTITUTION_VERSION` per semantic versioning rules:
   - MAJOR: removal or redefinition of an existing principle.
   - MINOR: new principle or section added.
   - PATCH: clarification, wording fix, non-semantic refinement.
3. Update `LAST_AMENDED_DATE` to the amendment date.
4. Run `/speckit.constitution` to propagate changes to dependent templates.

**Compliance review**: Every implementation plan MUST include a "Constitution Check" gate
(see `plan-template.md`) that verifies the plan does not violate any principle before
implementation begins.
